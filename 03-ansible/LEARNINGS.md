## 🎓 Чему я научился

В ходе выполнения ДЗ по Ansible я научился автоматизировать настройку Linux-сервисов на разных дистрибутивах, добиваться идемпотентности и проверять результат на чистых системах. Основное внимание уделил не только первому развёртыванию, но и поведению конфигурации при повторных запусках и изменении параметров.

### 🔷 Структура Ansible-проекта и роли
- Научился разделять автоматизацию на **playbook** и переиспользуемую **Ansible-роль** с каталогами `tasks`, `handlers`, `defaults`, `templates` и `files`.
- Освоил подключение отдельных групп задач через `import_tasks`, чтобы отделять установку пакетов, настройку репозиториев, JSON, nginx и cron.
- Научился выносить изменяемые параметры (`service_title`, `service_json_path`, `service_port`) в `defaults/main.yml` и переопределять их через `--extra-vars`.
- Закрепил работу с `inventory`, фактами Ansible и условиями `when` для разных операционных систем.

### 🔷 Кроссплатформенная автоматизация Linux
- Настроил одну роль для **Ubuntu 26.04** и **CentOS 7**, учитывая различия между `apt` и `yum`, а также между пакетами `cron` и `cronie`.
- Разобрался, как восстанавливать доступ к пакетам на устаревшей **CentOS 7** через архивные репозитории **CentOS Vault** и **EPEL**.
- Научился различать окружения с **systemd** и без него: на системах с менеджером служб используются Ansible-модули, а в минимальных тестовых контейнерах процессы запускаются напрямую.
- Увидел на практике, почему наличие установленного пакета ещё не означает, что сервис запущен и доступен.

### 🔷 Идемпотентность и управление состоянием
- Научился проектировать задачи так, чтобы **повторный запуск playbook не приводил к лишним изменениям** (`changed=0`).
- Использовал `stat` и `slurp` для проверки существующего JSON и чтения его содержимого перед изменением.
- Реализовал различие между двумя сценариями: при неизменном `title` сохраняется текущее состояние, а при смене `title` JSON пересоздаётся со сбросом `uptime`.
- Разобрался с **handlers** и `notify`: перезапуск nginx выполняется по изменению значимых настроек, а не при каждом запуске playbook.
- Проверял идемпотентность не только по `PLAY RECAP`, но и по фактическому **PID nginx** и содержимому HTTP-ответа.

### 🔷 Настройка nginx и HTTP
- Научился формировать конфигурацию nginx через **Jinja2-шаблон** с параметрами роли.
- Настроил обработку `GET /service_data`, при которой nginx отдаёт содержимое `/opt/service_state.json` с типом `application/json`.
- Разобрался с конфликтами стандартной конфигурации nginx и отдельного виртуального хоста.
- Освоил проверку синтаксиса nginx (`nginx -t`) и различие между **reload** (перечитать конфигурацию) и **restart** (перезапустить процесс).
- Понял, что изменение статического JSON само по себе не требует перезапуска nginx; в этом ДЗ перезапуск при смене `title` выполняется из-за отдельного требования к `uptime`.

### 🔷 Cron, shell-скрипты и работа с JSON
- Настроил ежеминутное cron-задание через модуль `ansible.builtin.cron`.
- Научился вычислять `uptime` по времени работы основного процесса nginx, используя PID-файл и `ps`, а не увеличивать счётчик произвольно.
- Использовал **`jq`** для обновления одного поля JSON с сохранением остальных данных.
- Вынес длинную команду cron в отдельный **shell-скрипт**, что упростило запуск вручную, диагностику и сопровождение.
- Применил запись через временный файл и `mv`, чтобы уменьшить риск выдачи клиенту частично записанного JSON.
- Разобрался с особенностями минимальных контейнеров: отсутствующие команды, ограниченное окружение cron и необходимость отдельно проверять выполнение задания.

### 🔷 Тестирование через Docker и WSL
- Использовал **WSL Ubuntu 22.04** как управляющую среду с Ansible, а **Docker** — для изолированных целевых Ubuntu 26.04 и CentOS 7.
- Освоил подключение к контейнерам через `community.docker.docker` **без SSH**.
- Научился отличать ошибки конфигурации от особенностей жизненного цикла контейнера: после `docker stop/start` процессы nginx и cron в контейнере с `sleep infinity` не восстанавливаются автоматически.
- Проверил роль на **чистых контейнерах**: первоначальная установка, HTTP `200 OK`, работа cron и повторный запуск с `changed=0`.
- Научился диагностировать ошибки по выводу Ansible, `docker exec`, `crontab -l`, `pgrep`, `curl` и содержимому файлов конфигурации.

### 🔷 Git, GitLab и автоматическая проверка
- Научился работать с проектом из **VS Code в режиме WSL**, сохраняя Linux-пути и окружение Ansible.
- Подключил локальный проект к существующему GitLab-репозиторию и работал в отдельной ветке `hwansible-task1`.
- Отделил исходники роли от локальных `inventory` и `.venv`, чтобы не отправлять тестовое окружение в репозиторий.
- Проверил решение через **GitLab CI**: задания для **CentOS** и **Ubuntu** завершились успешно.
- Убедился, что зелёный pipeline полезно дополнять локальными проверками поведения сервисов, особенно при изменении переменных и повторном запуске.

### 🔷 Главные выводы
- **Идемпотентность — это не только `changed=0`**: важно сохранять нужное состояние приложения и не перезапускать службы без причины.
- **Одна роль может работать на разных ОС**, если учитывать различия в пакетах, репозиториях и менеджерах служб.
- **Автоматизация должна работать на чистом окружении**, а не только на системе, которую уже настроили вручную.
- **Тестирование стоит разделять на этапы**: синтаксис Ansible, выполнение playbook, доступность HTTP, работу cron и проверку повторных запусков.

> **Граница проверенного:** CentOS 7 локально тестировался с Python 2.7.5; отдельной проверки на Python 2.6 не проводилось. Поддержка systemd предусмотрена в коде, но основные локальные тесты выполнялись в Docker-контейнерах без systemd.
