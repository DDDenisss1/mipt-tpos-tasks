# ⚙️ ДЗ #03: Ansible — Автоматизация настройки nginx и мониторинга uptime

## 💡 Основная идея
Необходимо с помощью Ansible автоматизировать настройку Linux-системы: установить необходимые пакеты, настроить nginx для выдачи JSON-файла по HTTP и организовать обновление времени работы nginx через cron.

Решение должно быть **идемпотентным**: повторное применение той же конфигурации не должно сбрасывать `uptime` и перезапускать nginx без необходимости.

## Подробное описание

С помощью Ansible необходимо выполнить следующие действия:

- Установить пакеты `nginx`, `cron`, `jq` (названия пакетов могут отличаться в разных дистрибутивах).
- Изменить конфигурацию nginx так, чтобы запрос **`GET /service_data`** возвращал содержимое файла `/opt/service_state.json`.
- Создать файл `/opt/service_state.json` со следующим начальным содержимым:

```json
{
  "title": "Seems working",
  "uptime": 0
}
```

- Обеспечить запуск nginx.
- Добавить cron-задание, выполняемое **раз в минуту** и обновляющее поле `uptime` в JSON-файле. `uptime` измеряется в минутах работы nginx.
- Проверить, что значение `uptime` в файле начинает изменяться.

### 🔹 Обновление uptime

В условии приведён пример однострочной команды с использованием `jq`, `ps` и PID nginx. Допускается использование `python-crontab` для автоматизации настройки cron.

При обновлении `uptime` значение поля `title` должно сохраняться.

### 🔹 Идемпотентность

**Обязательные требования:**

- Повторный запуск Ansible с той же конфигурацией **не сбрасывает** `uptime` в `/opt/service_state.json`.
- Повторный запуск Ansible с той же конфигурацией **не перезапускает** nginx.
- Если изменить значение `title` в шаблоне JSON (например, на `Seems work ok`) и повторно выполнить Ansible, файл `/opt/service_state.json` должен обновиться, а nginx — перезапуститься.
- Решение должно быть реализовано в виде **Ansible-роли**, которая импортируется из `playbook.yml` в корне репозитория.
- Одна и та же реализация должна работать на **Ubuntu 26.04** и **CentOS 7 (Python 2.6 — согласно формулировке задания)**.

## 🧪 Формат проверки

Проверяющая система запускает чистую виртуальную машину или окружение с требуемой ОС и выполняет `playbook.yml`.

### 1. Первоначальная настройка

Запускается `playbook.yml`, затем HTTP-запрос `GET /service_data` с помощью `curl` на **порт 80**.

Ожидаемый ответ:

```json
{
  "title": "Seems working",
  "uptime": 0
}
```

### 2. Обновление uptime

После паузы **X минут** повторяется `GET /service_data`.

Ожидаемый ответ:

```json
{
  "title": "Seems working",
  "uptime": X
}
```

### 3. Повторный запуск без изменений

`playbook.yml` запускается повторно. HTTP-запрос должен вернуть прежний `title`, а `uptime` **не должен сброситься**; nginx не должен перезапускаться.

```json
{
  "title": "Seems working",
  "uptime": X
}
```

### 4. Изменение title

Первая строка (значение `title`) в шаблоне изменяется, после чего снова запускается `playbook.yml`.

Ожидается обновлённый `title` и сброс `uptime` до нуля:

```json
{
  "title": "[Изменённая первая строка]",
  "uptime": 0
}
```

### 5. Повторное обновление uptime

После паузы **Y минут** запрос `GET /service_data` должен вернуть:

```json
{
  "title": "[Изменённая первая строка]",
  "uptime": Y
}
```

## 📋 Условия сдачи

- `playbook.yml` в корне репозитория и вызываемая им Ansible-роль.
- Решение должно быть проверяемым на чистом окружении без предварительной ручной настройки сервиса.
